# Attendee RSVP + Magic-Link Auth — Design (Phase 3)

## Overview

Builds the attendee-facing half of Open Party: opening a magic link (already generated by Phase 2's `publishEvent`, currently just displayed in the admin dashboard as an inert `/e/{token}` string), authenticating via it, and RSVPing — attendance, food/activity rankings, what they're bringing. This is the third of four phases; no WhatsApp sending exists yet (Phase 4), so links are still shared manually by the admin for testing, same as Phase 2 left them.

## Scope

**In scope:**
- `/e/[token]` magic-link landing route: validates the token, establishes an attendee session, redirects into the app
- `/` becomes the real "My Events" page (list of events the sessioned attendee is invited to)
- `/events/[eventId]` RSVP page: attendance, decline reason, food/activity ranking, bring-item claim, submit — editable while `published`, read-only once `finalized`
- A shared, generic session sign/verify primitive extracted from `src/lib/adminSession.ts`, with attendee sessions using a distinct signing context and cookie from admin sessions
- Middleware extended to gate `/events/*` on a valid attendee session

**Explicitly out of scope:**
- Any WhatsApp sending — invitations are still shared manually via the admin dashboard's displayed links (Phase 4)
- A "forgot my link" self-recovery flow — Foundation's decision stands: an expired/invalid link shows a friendly message, admin resends manually
- Automatic transition to `completed` — still deferred to Phase 4's scheduler
- Cleaning up `bringItems.assignedToUserId` (see "Data" below) — left alone, unused, to stay scoped

## Architecture

### Shared session primitive

`src/lib/adminSession.ts` currently hardcodes the admin signing context (`'admin-session:v1'`) inside `createSessionToken`/`verifySessionToken`. This phase extracts the generic HMAC sign/verify mechanics (Web Crypto, base64url token format) into a shared module — `signToken(context: string, payload: string, secret: string, now?): Promise<string>` / `verifyToken(context: string, token: string, secret: string, now?): Promise<boolean>` — and has both `adminSession.ts` (context `'admin-session:v1'`) and a new `attendeeSession.ts` (context `'attendee-session:v1'`) call into it. Two distinct cookie names (`admin_session`, `attendee_session`) mean the two session types can never be confused even if both cookies were somehow present on the same request. This directly addresses the collision risk the Phase 2 final review flagged.

Attendee sessions carry `userId` as their payload (not an expiry-only admin session) and use a 90-day expiry, refreshed every time a magic link is opened — long enough that an attendee checking back weeks later (before or after the event) doesn't need to dig up their original WhatsApp message.

### Magic-link flow

`/e/[token]` looks up the `eventInvitees` row by `inviteToken`. Three outcomes:
1. **Not found** or **`tokenExpiresAt` has passed**: render a friendly "this link is no longer valid, ask the organizer for a new one" page — no redirect, this page IS the response.
2. **Valid**: set/refresh the attendee session cookie (`userId` from the invitee's `userId`), redirect to `/events/[eventId]`.

The token itself is never re-displayed or re-usable as a session credential beyond this one validation step — from here on, the attendee session cookie carries their identity.

### Authorization split

Middleware gates `/events/*` on "does a valid attendee session cookie exist at all" (coarse, same pattern as `/admin/*`) — redirect to `/` if not. Each `/events/[eventId]` page additionally checks "is *this* sessioned user actually invited to *this* event" (a query, not middleware) — mirrors how the admin event detail page already does its own `notFound()` check beyond middleware's coarser gate.

## RSVP data model

No schema changes. All RSVP data already lives on `eventInvitees` (Foundation's schema): `rsvpStatus`, `declineReason`, `foodChoice1/2/3`, `activityChoice1/2/3`, `bringItemId`, `rsvpAt`. Submitting the RSVP form is an update to the sessioned user's own invitee row for that event — editable resubmission while the event is `published`, rejected (or simply not rendered as editable) once `finalized`.

**`bringItems.assignedToUserId`** is a column from Foundation's original schema that Phase 2 never used — the admin dashboard's attendee table already resolves "who's bringing what" entirely through `eventInvitees.bringItemId`. Phase 3 treats `eventInvitees.bringItemId` as the sole source of truth and does not write to `assignedToUserId`. This is a known, harmless unused column, not a bug — flagged here so it isn't mistaken for something Phase 3 forgot to wire up.

**Bring-item claiming**: on submit, if a `bringItemId` is selected, check no *other* invitee (`eventInvitees.bringItemId = X AND id != this invitee's id`) already holds it. Reject with a clear error if so. Re-selecting the same item they already hold is a no-op; switching from one item to another releases the old one implicitly (it was only ever referenced by their own row).

## Pages

- **`/` (My Events)**: no attendee session → today's Foundation-era placeholder copy, unchanged. Valid session → query every `eventInvitees` row for that `userId` (joined to `events` for title/date/status), list them with the attendee's own RSVP status, linking into `/events/[eventId]`.
- **`/events/[eventId]`**:
  - Event title/date/time/description.
  - Attendance: Yes / No. Declining shows an optional free-text reason field and skips the rest.
  - If attending: food ranking (three independent `<select>`s — 1st/2nd/3rd — populated from the event's non-disabled food options, all optional, rejected if two picks are the same non-empty option), activity ranking (identical shape), bring-item selection (optional, single-claim enforced as above).
  - Submit writes/updates the invitee row and sets `rsvpAt`.
  - Once the event is `finalized`: the interactive form is replaced by a read-only summary — final food, final activity, and what this attendee is bringing.

## Testing

Same light, integration-focused philosophy as every prior phase — real test DB, no mocks, targets business rules and auth primitives, not UI:
- `signToken`/`verifyToken`: generic round-trip, wrong secret, wrong context (a token signed under `'admin-session:v1'` must fail verification under `'attendee-session:v1'` and vice versa — this is the property the whole refactor exists to guarantee), tampered payload, expired token.
- Magic-link validation: valid token sets a session; expired token and nonexistent token both correctly fail (distinctly testable at the data layer, even if the user-facing page shows the same friendly message for both).
- RSVP submission: attendance write, decline-with-reason write, food/activity ranking write (including the reject-on-duplicate-rank rule), bring-item claim and the double-claim rejection, edit-while-published succeeding, write attempt against a `finalized` event being rejected.
- Middleware: valid attendee session → `/events/*` passes; no/invalid session → redirect to `/`; `/admin/*` behavior from Phase 2 stays unaffected (regression check, not new coverage).

No component/UI tests, consistent with every prior phase.
